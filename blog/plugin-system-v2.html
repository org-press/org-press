The Problem with V1

The original plugin system grew organically, accumulating complexity over time. What started as a simple way to handle code blocks evolved into a tangled web of special cases, hardcoded behaviors, and fragmented APIs.

Pain Points

  1. Fragmented Plugin Types - Block plugins, drawer plugins, and CLI plugins were all different interfaces
  2. Hardcoded Core Behaviors - TOC generation, heading IDs, and syntax highlighting were baked into core
  3. Complex Configuration - Users had to understand plugins, drawerPlugins, and internal registries
  4. Bridge Layer Hell - The v1/v2 coexistence created a compatibility layer that satisfied no one

The diagram above shows the v1 architecture: a bloated core with hardcoded behaviors, and three separate plugin interfaces that couldn't share logic.

Design Principles for V2

We started fresh with five guiding principles:

  1. Core is just orchestration - Pipeline stages + plugin registration, nothing else
  2. Everything is a plugin - TOC, headings, highlight, code blocks, drawers
  3. Simple things are simple - Factory functions for common patterns
  4. Complex things are possible - Full setup(ctx) API as escape hatch
  5. Leverage existing ecosystem - Rehype/uniorg plugins work directly

The New Architecture

The v2 architecture is clean and unified:

  • Core handles only orchestration
  • PluginRegistry loads and sorts plugins by priority
  • PluginContextImpl provides the setup() API for plugins
  • All plugins implement the same OrgPressPlugin interface

Factory Functions

Instead of implementing the full OrgPressPlugin interface, most plugins use factory functions:

FactoryPurposeExample Use Case
CreateDrawerTransform org drawers to HTMLAI assistant outputs, notes, warnings
CreateBlockHandle specific code block languagesPython, Ruby, custom DSLs
CreateTransformerPipeline stages for :useDOM rendering, server execution
CreateCommandCLI commandsorgp fmt, orgp lint
CreatePluginFull control escape hatchComplex multi-stage plugins

Before and After: Configuration

V1: Fragmented Configuration

// Old v1 config - multiple plugin arrays, confusing
export default {
  plugins: [javascriptPlugin, typescriptPlugin], // blocks only
  drawerPlugins: [aiDrawerPlugin],               // separate!
  // CLI plugins? Who knows where they go
};

V2: Unified Configuration

import { defaultPlugins, aiDrawerPlugin, CreateDrawer } from 'org-press';

export default {
  plugins: [
    ...defaultPlugins,  // All core functionality
    aiDrawerPlugin,     // Optional drawer
    CreateDrawer('NOTE', (d) => `<aside class="note">${d.html}</aside>`),
  ],
};

Before and After: Creating Plugins

V1: Different Interfaces for Different Things

// Block plugin (v1)
const myBlockPlugin: BlockPlugin = {
  name: 'python',
  languages: ['python', 'py'],
  transform: async (block, ctx) => ({ code: block.value }),
};

// Drawer plugin (v1) - completely different interface!
const myDrawerPlugin: DrawerPlugin = {
  name: 'ai-drawer',
  drawers: ['AI'],
  transformDrawer: (drawer, ctx) => `<div>${drawer.html}</div>`,
};

// CLI plugin (v1) - embedded in BlockPlugin?!
const myCLIPlugin: BlockPlugin = {
  name: 'formatter',
  cli: {
    command: 'fmt',
    description: 'Format code',
    execute: async (args, ctx) => { /* ... */ return 0; },
  },
};

V2: Consistent Factory Functions

import { CreateBlock, CreateDrawer, CreateCommand } from 'org-press';

// Block handler - clean factory
const pythonPlugin = CreateBlock('python', {
  languages: ['python', 'py'],
  transform: (code, ctx) => ({ html: `<pre>${code}</pre>` }),
});

// Drawer handler - same pattern
const aiDrawer = CreateDrawer('AI', (drawer) =>
  `<details class="ai"><summary>AI</summary>${drawer.html}</details>`
);

// CLI command - same pattern
const fmtCommand = CreateCommand('fmt', {
  description: 'Format code blocks',
  args: [{ name: 'check', type: 'boolean', description: 'Check only' }],
  execute: async (args, ctx) => { /* ... */ return 0; },
});

The Presets System

Instead of magic configuration resolution, v2 uses simple arrays: 

// Use defaults - most common
const defaultConfig = {
  plugins: [...defaultPlugins],
};

// Add optional plugins
const withOptionalPlugins = {
  plugins: [...defaultPlugins, aiDrawerPlugin, noteDrawerPlugin],
};

// Start minimal, add only what you need
const minimalConfig = {
  plugins: [
    ...minimalPlugins,
    domPlugin,
    CreateDrawer('AI', (d) => `<div>${d.html}</div>`),
  ],
};

Plugin Context API

For advanced use cases, CreatePlugin provides full access to the plugin context: 

import { CreatePlugin } from 'org-press';

const analyticsPlugin = CreatePlugin('analytics', (ctx) => {
  // Register lifecycle hooks
  ctx.hook('build:start', () => console.log('Build started'));
  ctx.hook('build:end', (stats) => sendToAnalytics(stats));

  // Register multiple drawer handlers
  ctx.onDrawer(['NOTE', 'WARNING', 'TIP'], (drawer) =>
    `<div class="callout callout-${drawer.name.toLowerCase()}">${drawer.html}</div>`
  );

  // Register block handler with custom matching
  ctx.onBlock({
    matches: (block) => block.language === 'chart' || block.meta?.includes(':chart'),
    transform: (code, blockCtx) => ({
      html: renderChart(JSON.parse(code)),
      script: `initChart('${blockCtx.blockId}')`,
    }),
  });

  // Add CLI command
  ctx.addCommand('stats', {
    description: 'Show content statistics',
    execute: async (args, cmdCtx) => {
      const stats = await gatherStats(cmdCtx.contentDir);
      console.table(stats);
      return 0;
    },
  });
});

Migration Guide

Migrating from v1 to v2 is straightforward:

Step 1: Update imports

// Before
import { loadPlugins, BlockPlugin } from 'org-press';

// After
import { defaultPlugins, CreateBlock, OrgPressPlugin } from 'org-press';

Step 2: Update config

// Before
export default {
  plugins: [...myPlugins],
  drawerPlugins: [...myDrawerPlugins],
};

// After
export default {
  plugins: [...defaultPlugins, ...myPlugins, ...myDrawerPlugins],
};

Step 3: Convert custom plugins

// Before: v1 BlockPlugin
const myPlugin: BlockPlugin = {
  name: 'custom',
  drawers: ['CUSTOM'],
  transformDrawer: (drawer) => `<div>${drawer.html}</div>`,
};

// After: v2 factory
const myPlugin = CreateDrawer('CUSTOM', (drawer) =>
  `<div>${drawer.html}</div>`
);

Summary

The v2 plugin system delivers on its promises:

AspectV1V2
Plugin interfaces3 different types1 unified interface
Configurationplugins + drawerPluginsSingle plugins array
Core behaviorsHardcodedAll pluggable
Learning curveSteepGradual (factories)
EcosystemIsolatedRehype/uniorg compatible
ExtensibilityLimitedFull setup(ctx) API

The result is a plugin system that's simple for common cases, powerful for advanced cases, and consistent throughout. 

// This is all you need for most projects
import { defaultPlugins } from 'org-press';

export default {
  plugins: [...defaultPlugins],
};
